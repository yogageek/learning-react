# Chapter 10 Testing Notes

## 為什麼 `npm test` 會報 `react-scripts` 找不到

如果在 `chapter-10/testing` 執行：

```powershell
npm test
```

出現：

```text
'react-scripts' 不是內部或外部命令
```

代表目前這個專案需要的 `react-scripts` 沒有被安裝在可解析的位置。

`chapter-10/testing/package.json` 需要：

```json
"react-scripts": "3.4.1"
```

但外層 `D:\vibecode\learning-react\node_modules` 原本是另一個 Vite 專案的依賴，不一定有 `react-scripts`。

## 為什麼明明安裝了還會有 ESLint 衝突

`chapter-10/testing` 是舊版 CRA：

- `react-scripts@3.4.1`
- 需要 `eslint@^6.6.0`

外層 `D:\vibecode\learning-react` 是另一個較新的專案，安裝的是：

- `eslint@9.39.4`

即使 `chapter-10/testing` 自己已經有：

- `node_modules`
- `package-lock.json`
- `eslint@6.8.0`

CRA 的 preflight check 還是會往上掃，看到外層 `eslint@9.39.4` 就報衝突。

也就是：

- 內層專案依賴其實裝好了
- 但外層 `node_modules` 干擾了 CRA 檢查

## 先讓測試跑起來的做法

在 `chapter-10/testing/.env` 加：

```env
SKIP_PREFLIGHT_CHECK=true
```

這樣可以跳過 CRA 的 preflight check。

注意：這只是先跑起來，不代表巢狀專案結構本身是乾淨的。

## 為什麼不建議所有 chapter 共用同一份 `node_modules`

因為不同章節的依賴版本可能不同。

例如：

- 外層專案用 React 18 + Vite
- `chapter-10/testing` 用 React 16 + CRA 3

如果強行共用一份 `node_modules`，常見問題是：

- `react-scripts` 版本不相容
- `eslint` 版本衝突
- 測試工具鏈互撞

## `npm install` 會不會用到 `package-lock.json`

在某個資料夾執行：

```powershell
npm install
```

npm 會優先參考該資料夾自己的：

- `package.json`
- `package-lock.json`

如果 `chapter-10/testing` 原本沒有自己的 `package-lock.json`，第一次 `npm install` 後會在這個資料夾產生新的 lock 檔。

也就是說，這個 chapter 可以有自己獨立的 lock，不一定跟外層共用。

## 為什麼 `npm test` 體感很慢

不是因為只有一行 `expect`，就一定會瞬間結束。

`react-scripts test` 會先做這些事：

- 啟動 Jest
- 載入 CRA 設定
- 跑 Babel 轉譯
- 初始化測試環境
- 預設進入 watch mode

所以就算測試檔很少，啟動成本還是在。

如果只想跑一次，不要進 watch mode：

```powershell
npm test -- --watchAll=false
```

更單純一點：

```powershell
npm test -- --watchAll=false --runInBand
```

這樣會：

- 跑完就結束
- 不常駐監看
- 小專案通常更穩定

## 為什麼 Git Bash 裡 `npm` 指令按 `Tab` 沒提示

你當時的終端機是：

```text
MINGW64
```

也就是 Git Bash。

Git Bash 預設通常只有基本的路徑補全，不一定有完整的 `npm` command completion。

所以：

- `cd chap<Tab>` 可能能補資料夾
- `npm ru<Tab>` 不一定會補 `run`

這不是 npm 壞掉，是 shell completion 沒設好。

如果要比較好的命令提示，通常改用 VS Code 的 PowerShell 體驗會比較好。

## VS Code 哪裡開 auto import 設定

### 全域設定

按：

```text
Ctrl + Shift + P
```

輸入：

```text
Preferences: Open User Settings (JSON)
```

### 專案設定

按：

```text
Ctrl + Shift + P
```

輸入：

```text
Preferences: Open Workspace Settings (JSON)
```

可加入：

```json
{
  "javascript.suggest.autoImports": true,
  "typescript.suggest.autoImports": true
}
```

如果希望 `chapter-10/testing` 自己控制，通常放在：

`chapter-10/testing/.vscode/settings.json`

## 怎麼盡量避免 VS Code ESLint 吃到外層

在 `chapter-10/testing/.vscode/settings.json` 可加：

```json
{
  "eslint.workingDirectories": [
    {
      "directory": ".",
      "changeProcessCWD": true
    }
  ]
}
```

這樣 VS Code 的 ESLint extension 會盡量以目前專案資料夾為工作目錄。

注意這只能影響 VS Code extension 的解析方式，不一定能解 CRA 執行時的 preflight 掃描問題。

## 滑鼠移上去想看到更完整函式說明

這是 VS Code 的 Hover / IntelliSense 能力。

建議：

1. 開啟 hover
2. 加 `jsconfig.json`
3. 在函式上寫 JSDoc

可在設定加：

```json
{
  "editor.hover.enabled": true,
  "javascript.suggest.enabled": true,
  "typescript.suggest.enabled": true
}
```

在 JS 專案加 `jsconfig.json`：

```json
{
  "compilerOptions": {
    "checkJs": true,
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "Node"
  },
  "include": ["src"]
}
```

如果函式有 JSDoc，hover 提示會更完整。

例如：

```js
/**
 * Add two numbers together.
 * @param {number} a
 * @param {number} b
 * @returns {number}
 */
export const sum = (a, b) => a + b;
```

## `describe` 是做什麼的

`describe` 用來把相關測試包成一組，方便閱讀與輸出整理。

例如：

```js
describe("functions", () => {
  test("Multiplies by two", () => {
    expect(timesTwo(4)).toBe(8);
  });
});
```

好處：

- 輸出結構更清楚
- 同類測試可放一起
- 後面擴充比較自然

## `Checkbox` 元件的邏輯

```jsx
export function Checkbox() {
  const [checked, setChecked] = useReducer(
    checked => !checked,
    false
  );

  return (
    <label>
      {checked ? "checked" : "not checked"}
      <input
        type="checkbox"
        value={checked}
        onChange={setChecked}
      />
    </label>
  );
}
```

重點：

- `checked` 是目前勾選狀態
- 初始值是 `false`
- `setChecked` 每次觸發會把狀態反轉
- 三元運算子控制畫面顯示 `"checked"` 或 `"not checked"`

比較正規的 checkbox 綁定通常寫：

```jsx
checked={checked}
```

比 `value={checked}` 更合適，因為 checkbox 真正控制的是 `checked` 屬性。

## `getByLabelText(/not checked/i)` 是什麼意思

這行：

```js
const checkbox = getByLabelText(/not checked/i);
```

意思是：

- 用 label 顯示文字找出對應的表單元素
- `/not checked/i` 是正規表達式
- `i` 代表不分大小寫

可理解成：

```js
// 用 label 文字找到對應的 checkbox。
const checkbox = getByLabelText(/not checked/i);
```

這種寫法比用 class 或 id 更接近使用者操作方式，所以很常見。

## `data-testid="checkbox"` 要寫在哪

不是寫在 test 檔裡，而是寫在元件 JSX 上。

例如：

```jsx
<input
  type="checkbox"
  data-testid="checkbox"
  checked={checked}
  onChange={setChecked}
/>
```

然後測試裡再用：

```js
const checkbox = getByTestId("checkbox");
```

不過 Testing Library 一般建議優先使用：

1. `getByRole`
2. `getByLabelText`
3. `getByText`
4. `getByTestId`

`data-testid` 通常是最後手段。

## 怎麼看 coverage report

coverage report 打開後，最重要看的是：

- 上方百分比
- 左邊行號旁的執行次數
- 哪裡是綠色、紅色、黃色

例如：

- `100% Statements 3/3`
- `100% Branches 2/2`
- `100% Functions 2/2`
- `100% Lines 3/3`

代表：

- 3 個 statement 都被跑到
- 2 個 branch 都被跑到
- 2 個 function 都被跑到
- 3 行可執行行都被跑到

### `3x` 是什麼

左邊的 `3x` 代表該行被執行了 3 次。

在 `Checkbox` 範例中很合理，因為：

1. 初始 render 1 次
2. 點一下 re-render 1 次
3. 再點一下 re-render 1 次

所以某些關鍵行會顯示 `3x`。

### 為什麼只有某些單字是綠色

不是只有那些單字有被測到。

coverage 視圖是：

- 語法高亮
- coverage 標示

疊在一起顯示。

真正要看的是：

- 左邊有沒有 `3x`
- 行底色是不是綠色
- 上方是不是 `100%`

不是只看某個單字有沒有被染成綠色。

## 這次對話的核心結論

- `chapter-10/testing` 是巢狀 CRA 專案，容易被外層 `node_modules` 干擾
- `SKIP_PREFLIGHT_CHECK=true` 可以先跳過 CRA 的 preflight
- `npm test -- --watchAll=false --runInBand` 比較適合只跑一次
- VS Code 的 auto import、hover、ESLint 工作目錄都可以用 workspace 設定控制
- Testing Library 優先用使用者視角的查詢方式，例如 `getByLabelText`
- coverage 判讀時重點看執行次數與整體 coverage，不是只看綠色單字
- npm test -- --coverage  產生覆蓋結果 目錄下產出coverage資料夾 裡面有一份html可直接查看
