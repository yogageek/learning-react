# Chapter 12: Client Fetching 學習筆記

## 核心重點：環境差異與同構開發 (Isomorphic Development)

本章節透過 `client-fetching` 與 `node-fetching` 的對照，展示了在 React 伺服器端渲染 (SSR) 脈絡下最重要的基礎概念。

### 1. 瀏覽器端資料獲取 (Client-Side Fetching)
*   **工具：** 使用瀏覽器原生內建的 `fetch` API。
*   **特性：** 直接在客戶端執行，由使用者的瀏覽器發出請求。
*   **範例：** `index.html` 中的 `<script>` 區塊。

### 2. 環境差異對照 (Runtime Differences)
*   **瀏覽器環境：** 擁有全域的 `window` 物件與 `fetch` API。
*   **Node.js 環境：** 傳統上沒有內建 `fetch`，需依賴第三方套件（如 `node-fetch`）。
*   **重要性：** 撰寫 SSR 應用時，同一段代碼可能在兩端執行，必須考慮 API 的可用性。

### 3. 同構概念 (Isomorphic / Universal)
*   **定義：** 指的是同一份程式碼可以同時在「伺服器端」與「客戶端」無縫執行。
*   **應用場景：** 在 SSR 中，React 組件首次渲染發生在伺服器，後續互動則切換到客戶端。因此，資料抓取的邏輯必須具備同構性。

### 4. 為 SSR (Server-Side Rendering) 鋪路
*   理解環境差異是為了銜接後續的 **Next.js** 或自建 SSR 架構。
*   SSR 的第一步就是解決「伺服器端如何預先取得資料並渲染成 HTML」的問題。
*   常見使用情況: 原本都是服務端(伺服器)渲染。現在要把一部分改為用戶端(瀏覽器)渲染，希望程式碼可共用，不想改太多

# React SSR 与 Hydration 对话重点总结

## 一、SSR 的基本流程（手动实现版）

1. **服务器端（Express）**
   - 使用 `ReactDOMServer.renderToString(<Menu />)` 将 React 组件转换成 HTML 字符串。
   - 读取 `./build/index.html` 模板（原本 `<div id="root"></div>` 为空）。
   - 用生成的 HTML 字符串替换 `<div id="root"></div>` 的内容。
   - 将完整 HTML 返回给浏览器。
   - 同时通过 `express.static('./build')` 托管静态 JS/CSS 文件。

2. **客户端（浏览器）**
   - 收到完整 HTML 后立即显示内容（不等待 JS）。
   - 下载并执行 `main.js`。
   - 调用 `ReactDOM.hydrate(<Menu />, document.getElementById('root'))`。
   - React 复用现有 DOM，只附加事件监听和内部状态，不重建节点。

## 二、什么是 Hydration（注水）？

- **定义**：将服务器生成的静态 HTML 与客户端 React 的事件、状态绑定起来的过程。
- **比喻**：服务器给你一幅已经画好的素描（HTML），hydrate 就是在上面描上数字并连接起来，使其变成可连线的互动图画。
- **结果**：页面既保留完整内容，又获得 `onClick` 等交互能力。

## 三、Hydration 发生在何时？

- **多页面应用（MPA）**：每次整页刷新都会重新执行 hydration。
- **单页面应用（SPA）+ SSR（如 Next.js）**：只在首次加载页面时执行一次，后续客户端路由切换不再 hydration。
- **Islands 架构（如 Astro）**：每个需要交互的组件可独立、延迟 hydration。

## 四、Hydration 前后客户端拥有什么？

| 项目                 | Hydration 前                  | Hydration 后                         |
| -------------------- | ----------------------------- | ------------------------------------ |
| 真实 DOM 节点         | 有（来自服务器）              | 有（同一个节点，未重建）             |
| 事件监听             | 无                            | 有（React 事件委派系统）             |
| React 内部状态       | 无                            | 有（state, props, refs）             |
| Virtual DOM / Fiber  | 无                            | 有                                   |
| 后续更新能力         | 需要整页刷新                  | 有（`setState` 驱动局部更新）        |
| 用户可交互           | 否                            | 是                                   |

## 五、没有 Hydration 会怎样？

- 服务器返回完整 HTML，但页面是**静态的**——按钮无法点击，无任何动态交互。
- 只能通过整页刷新或传统表单提交来更新内容。

## 六、哪些部分应该被 Hydration？

**需要 hydration 的典型 UI：**
- 整个应用（SSR + SPA 场景）
- 表单、输入框、搜索栏
- 交互按钮（点赞、购物车、展开/收起）
- 轮播图、选项卡、下拉菜单
- 需要实时更新的数据（时钟、股票报价、留言列表）

**不需要 hydration 的部分：**
- 纯静态文本、图片、布局结构（无交互、无状态变化）

## 七、Hydration 是手动还是自动？

- **默认（框架如 Next.js）**：全自动。你只需写 React 组件，框架负责调用 `hydrateRoot`、注入初始数据等。
- **手动实现（教学目的）**：需要自己写 `ReactDOM.hydrate`，并确保服务器与客户端的 props 数据完全一致（否则会报 "Text content did not match" 错误）。
- **进阶优化（手动标记部分 hydration）**：如 Gatsby 的 `"use client"` 指令、React 的 `<Suspense>` 或第三方懒加载库。

## 八、为什么教学示例要让你手动写这么多？

- **教育目的**：让你理解 SSR 不是魔法，而是 `renderToString` + 字符串替换 + `hydrate` 的组合。
- **掌握原理**：当框架出错（如 hydration mismatch）时，你具有底层认知去排查。
- **历史背景**：早期 React 生态没有成熟框架时，许多团队确实这样手写。

## 九、手动实现与框架（Next.js）的对比

| 手动实现（教学示例）                 | Next.js 自动处理                      |
| ------------------------------------ | ------------------------------------- |
| 写 Express 服务器、设置 port          | 内置服务器，无需编写                   |
| `app.use(express.static('./build'))` | 自动托管静态资源                       |
| `app.get('/*')` 手动匹配所有路由      | 基于 `pages/` 或 `app/` 目录自动路由   |
| 手动调用 `renderToString`             | 自动对每个页面进行 SSR                 |
| 读取并替换 `index.html`               | 自动生成并注入 HTML                    |
| 手动调用 `ReactDOM.hydrate`           | 自动执行 `hydrateRoot`                 |
| 手动传递相同 props（常写死在客户端）   | 通过 `__NEXT_DATA__` 自动序列化同步数据 |

## 十、核心结论

1. **SSR = 服务器生成完整 HTML + 客户端 hydrate**。
2. **Hydrate 是让静态页面变得可互动的关键一步**，只发生在页面加载（或特定组件进入时）。
3. **默认情况下，现代框架完全自动化 hydration**，无需开发者手动干预。
4. **手动实现是为了学习原理**，生产环境请直接使用 Next.js、Remix、Gatsby 等成熟方案。
5. 理解 hydration 后，你能更好地调试常见的 “Text content did not match” 错误，并决定哪些组件需要部分 hydration 来优化性能。
